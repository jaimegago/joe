This project uses a session-tracking convention that joins chat sessions to Claude Code sessions, commits, and decisions through a single slug. The full convention is specified in docs/project/pm-convention.md.

Slug assignment: when a chat is about to produce its first Claude Code prompt that writes a commit, assign it a slug. If the work corresponds to an existing file under docs/backlog, the slug is that filename without extension. If the work is infrastructure or bootstrap with no backlog file, mint a short kebab-case slug. Read-only investigations that only report back in chat get no slug; investigations that write a committed findings file do.

Per chat: the first time you assign a slug, give me two things to paste — the slug as the first line of the Claude Code prompt in the form "Session: <slug>", and a chat title string in the form "<slug> — <short description>" for me to rename the chat. Add a two-digit suffix (slug-01, slug-02) only when one thread spawns multiple Claude Code build sessions.

Every build prompt you emit must instruct Claude Code, as acceptance criteria, to: begin the commit message with the slug; if a decision was made or changed, append an entry to docs/project/DECISIONS.md in the existing format with a Session field set to the slug; if an architectural invariant, command, or convention changed, update CLAUDE.md; if open or deferred work remains, write or update docs/backlog/<slug>.md; whenever any backlog file is created, changed, or archived, regenerate docs/backlog/INDEX.md; when a thread is finished, move its backlog file to docs/backlog/done; and push the commit to origin/main, not only commit it locally. A commit that is committed but not pushed is invisible to this project's synced files, so the push is part of "done."

New backlog files use this format: first line is the title, second line is a status of open or in-progress, then up to two optional lines, then the body. The two optional lines, when present, sit immediately after the status line. Priority: exactly one of now, next, later — now means the item is on the current working horizon and should be picked from first, next means queued immediately behind the current horizon, later means no horizon; an absent Priority line means untriaged. Blocked-by: names either a backlog slug or the form "external (short note)" — it is a one-directional edge, with no Blocks or Related field and no reverse-edge maintenance. Blocked-by is the canonical dependency line going forward; pre-existing informal variants such as "Depends on:" in older files are left as-is and get normalized during a triage pass, not opportunistically. The INDEX Priority column follows Status and carries the item's Priority value; an item with no Priority line renders as a blank cell, never a default. Blocked-by does not appear in INDEX.

Volatile, growth-driven counts (edge types, migrations, and similar) must never be hardcoded as fixed numbers in CLAUDE.md; express them structurally or as pointers, per D-0032.

Grounding: CLAUDE.md, docs/project/DECISIONS.md, and docs/backlog/INDEX.md are synced into this project from GitHub. Before strategizing or making any architectural decision, consult them so you do not re-litigate settled decisions or contradict current state. The sync is a manual snapshot of pushed state; if recent Claude Code work has landed, remind me to Sync before relying on these files. INDEX.md carries backlog titles, status, and priority only; for an item's detail — including its Blocked-by line — ask me to provide its docs/backlog/<slug>.md body.

Commits go straight to main; never reference feature branches.

CC session reports are consumed by the chat model, never read by a human: instruct CC to write them wrapped in a single triple-backtick fenced code block so the whole report can be copied in one click, as plain terse prose with minimal numbered lists, keeping file:line citations and VERIFIED/UNVERIFIED tags, and to omit all decoration — no banner or separator lines, no box-drawing characters, no ALL-CAPS headers, nothing ornamental.

Model recommendation: whenever you emit a Claude Code prompt, append one line outside the code block recommending a specific model and effort level for that prompt. Use current Claude Code model names (as of this writing: Fable 5, Opus 4.8, Sonnet 4.6, Haiku 4.5 — verify names in-session if uncertain) and named effort levels (low, medium, high, xhigh, max). Do not use tiers. Derive the recommendation from the actual prompt just written, not from a fixed category table: weigh ambiguity of the task, blast radius of a wrong edit, number of files and cross-cutting concerns, and how much verification discipline the prompt demands. Include a one-clause rationale tied to the specific prompt. Hard floors, not defaults: anything touching the governance seam, RBAC, or a break-tested invariant never goes below Opus 4.8 at xhigh; pure read-only Phase 1 verification never needs more than Sonnet at medium. Between the floors, exercise judgment per prompt.
